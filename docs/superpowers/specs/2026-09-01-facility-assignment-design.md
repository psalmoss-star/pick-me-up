# 시설 배치(assignment) — 설계

> 범위: `facility-upgrade-proposal.md`의 **제안 A만**. 제안 B(출정 준비 한 수)·C(층=계급 시각화)는 이번 범위 밖이다.
> 작성 2026-09-01. 채택되면 gdd-v3 §4.5에 반영하고 제안 문서는 폐기한다.

---

## 1. 무엇을 왜

지금 잉여 영웅의 출구는 **제물**과 **모험 파견** 둘이다. 배치는 세 번째 출구이며,
앞의 둘과 성격이 다르다 — 갈아 없애지도, 내보내지도 않고 **곁에 두고 일을 시킨다.**

| 축 | 파견 | 배치 |
|---|---|---|
| 수명 | 일회성 (N전투 뒤 종료) | **영구 상태** (해제할 때까지) |
| 보상 | 그 영웅의 exp·재료 | **시설 효과 상승** (파티 전체가 받음) |
| 위험 | 부상 | 없음 |
| 성장 | 한다 | **안 한다** |

보상의 *종류*가 달라서 유휴 exp와 경쟁하지 않는다. 이것이 이 설계의 축이다.

## 2. 확정된 결정 (사용자, 2026-09-01)

1. **배치 = 영구 상태, 파견 = 일회성 이벤트.** 배치는 exp 대신 시설 효과를 준다.
2. **보너스는 합성소·훈련소만.** `restHeal`·`armoryAtk`는 전투력에 직접 닿는 칼날이라 제외한다
   (`data/facilities.ts` 파일 주석). 그 결과 **climb-check 재수렴이 필요 없다.**
3. **배치자 본인은 유휴 exp를 못 받는다.** 안 그러면 교관이 자기 자신을 가르친다.

## 3. 핵심 근거 — 이미 있는 패턴을 쓴다

`runStore.ts`가 파견 인원을 유휴 exp에서 제외하며 이렇게 적어 뒀다:

> ⚠️ 파견 중인 영웅은 제외한다(`awayNow`). 유휴 exp와 모험 exp를 둘 다 받으면
> 파견이 순이득이 되어 같은 함정에 정면으로 걸린다 — 대기실에 두는 것보다
> 항상 나으므로 "일단 다 내보내기"가 유일한 최적해가 된다.

배치는 **같은 함정의 세 번째 사례**다. 새 패턴을 만들지 않고 이 조건에 한 항만 더한다.

### 부등식이 튜닝이 아니라 구조로 지켜진다

제안 문서의 수용 기준 "배치 이득 < 출전 성장"은, 배치자가 exp를 **0** 받으므로
구조적으로 참이다. 수치를 조여서 지키는 것이 아니다. 이 안을 고른 진짜 이유가 이것이다.

> gdd-v3 §4.5 — 훈련소는 전투에 안 나간 영웅만 준다. 참전자와 경쟁시키면
> "안 내보내는 게 이득"이 되어 퍼머데스의 긴장이 사라진다.

## 4. 데이터 구조

```ts
/** 배치를 받는 시설 — 전투력에 안 닿는 둘뿐이다 */
export type AssignableFacility = 'training' | 'forge';

/** 시설 → 배치된 영웅 instId 목록 */
assignments: Record<AssignableFacility, HeroInstId[]>;
```

⚠️ **`Record<FacilityKind, ...>`가 아닌 이유.** 숙소·무기창고를 키로 가지면
"왜 여긴 항상 비어 있지?"가 되고 다음 사람이 채운다. 타입이 금지하면
그 실수가 **컴파일 에러**가 된다.

### 수치 (전부 `data/facilities.ts`, 코드에 하드코딩 금지)

```ts
export const ASSIGN_SLOTS: Record<AssignableFacility, number> = { training: 2, forge: 2 };
export const ASSIGN_BONUS = { training: 25, forge: 0.05 } as const;
```

- 훈련소: 유휴 exp **+25/인** (절대값)
- 합성소: 전환율 **+5%p/인**

⚠️ **합성 전환율은 1.0에서 클램프한다.** `FORGE_RATE` 만렙 0.95 + 0.10 = 1.05인데,
제물 가치보다 많이 나오면 합성이 exp 생성기가 된다.

### 파생 함수 — 화면이 직접 더하지 않는다

```ts
export function idleExpWithAssign(level: number, assigned: number): number
export function forgeRateWithAssign(level: number, assigned: number): number
```

`FacilityScreen.tsx`가 이미 경고하는 함정이다 — 화면이 수치를 다시 계산하면
표시와 실제가 갈라진다.

## 5. 규칙 4개

1. **배치자는 유휴 exp를 못 받는다.** `runStore.ts`의 `!awayNow.has(...)` 옆에
   `!assignedNow.has(...)`를 더한다.
2. **출전하면 그 층 동안 산출이 멈춘다.** 배치자가 이번 전투에 참전했으면(`fought`)
   보너스 계산에서 뺀다. 배치를 *해제하는 게 아니라* 이번 층만 안 센다 —
   "전투력과 생산의 제로섬".
3. **사망 시 자동 해제.** 퍼머데스 단일 지점에서 배치 목록도 청소한다.
4. **제물이 되면 자동 해제.** `fuse()`가 `consumedInstId`를
   "호출자가 반드시 제거해야 한다"고 넘기는 그 지점이다.

⚠️ 3·4를 빠뜨리면 유령 instId가 슬롯을 **영구 점유**한다 —
HANDOFF §"교착은 못 하는 게 아니라 못 빠져나오는 것"이 정확히 이 모양이다.
묶는 기능을 넣을 때 푸는 쪽을 무조건으로 둔다.

## 6. 저장

`SavedRun`에 `assignments`를 더한다. 로드 검증은 **파견과 같은 방식**:

- 로스터에 없는 / 죽은 instId는 버린다 (유령 = 교착)
- 슬롯 수를 넘으면 앞에서 자른다 (수동 편집 방지)
- 같은 영웅이 두 시설에 있으면 뒤엣것을 버린다
- 없는 세이브는 빈 배치로 읽는다

`SAVE_VERSION`은 **올리지 않는다** — 기본값(빈 배치)이 안전하므로 마이그레이션이 필요 없다.

## 7. 테스트 (TDD)

| # | 테스트 |
|---|---|
| 1 | 배치자는 유휴 exp를 못 받는다 |
| 2 | **배치 이득 < 출전 성장** (문서의 핵심 부등식) |
| 3 | 배치자가 출전하면 그 층 산출이 0 |
| 4 | 사망 시 자동 해제 |
| 5 | 제물이 되면 자동 해제 |
| 6 | 슬롯 초과 배치가 거부된다 |
| 7 | 저장/불러오기 왕복 보존 |
| 8 | 유령 instId가 로드에서 걸러진다 |
| 9 | 합성 전환율이 1.0을 안 넘는다 |
| 10 | 회차 시작 시 배치가 초기화된다 (§계승 금지) |

## 8. 재측정

**밸런스 재측정 의무 없음.** 합성소·훈련소는 `sim`도 `climb-check`도 쓰지 않는다
(`FORGE_RATE` 주석: "층별 승률과는 무관하다").

⚠️ 다만 **그 주장을 믿지 말고** 구현 후 `climb-check`를 한 번 돌려
정말 미동이 없는지 확인한다. HANDOFF §"테스트는 깨뜨려봐야 믿는다"의 같은 태도다.

## 9. 이번 범위 밖

- **제안 B (출정 준비 한 수)** — 유일하게 승률을 미는 것이라 마지막에 한다.
  하려면 `npm run sim` + `climb-check` 둘 다 필요하다.
- **제안 C (층=계급 시각화)** — 순수 연출이라 언제 해도 된다.
- **유휴 exp를 "배치자만"으로 바꾸는 것** — 밸런스 변경이다. 1차에서는
  기존 유휴 exp를 그대로 두고 배치 보너스를 얹는다.
