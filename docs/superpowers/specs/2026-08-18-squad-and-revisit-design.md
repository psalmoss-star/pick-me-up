## 1. 발단 — HANDOFF §STEP 28의 진단이 틀렸다

§STEP 28이 "이제는 진짜 누적 소모"라고 결론지었는데, **실측으로 반증됐다.**

```
생성 81~100 / 회복 65%   패배 300 · 전멸 0 · 완주 0
                         패배 시 파티HP 평균 98% · 생존 3.54명
```

전멸률이 전 구간 **0%**고 패배 시점 HP가 **95~98%**다.
**만피로 들어가서 그 층에 지는 것**이지 소모가 아니었다.

그래서 회복률 손잡이가 무효다 — 65% → 100%로 올려도 61~80 구간이
**11% → 9%로 오히려 내려갔다.** §STEP 28이 남긴 "남은 손잡이 셋" 중
**회복 수단 상향은 여기서 폐기된다.**

> 이건 §5-53("패배로 끝났다와 전멸로 끝났다를 구분해서 세라")을 §STEP 28이
> 스스로 적어놓고 그 다음 단계에서 다시 밟은 것이다. 2차 기록에 "전멸률 0%"가
> 이미 적혀 있었는데도 결론은 "누적 소모"로 갔다.

### 듣는 손잡이는 정원 하나뿐이었다

```
정원 | 생성 21~40    41~60       61~80       81~100
  3  | 16.20(72%)  12.04(32%)   9.99(17%)  10.67( 1%)
  4  | 20.00(100%) 19.95(100%) 19.56(94%)  19.69(83%)
  5  | 20.00(100%) 20.00(100%) 20.00(100%) 20.00(100%)
```

**정원 5는 전 구간 100%다.** 300회 중 한 번도 안 막혔다.
목표치(25~40%)를 넘는 정도가 아니라 **탑이 통째로 사라진다.**

> ⚠️ **로스터 두께가 독립 변수다.** 위 표의 정원 3 수치(17%/1%)가 §STEP 28 기록
> (11%/0%)보다 높은 것은 로스터를 5인 → 8인으로 늘렸기 때문이다.
> 대기 인원이 많으면 사망을 메꿀 여유가 생긴다. **2군 시스템은 로스터를 키우는
> 방향이므로 이 효과도 같이 들어온다** — 정원 효과와 섞이지 않게 따로 잴 것.

## 2. 확정된 설계 결정

| 항목 | 결정 |
|---|---|
| 100층 완주 | **한 런 안에서 가능해야 한다** (§STEP 28의 "구간 목표 재정의"가 이걸로 결론남) |
| 파밍 | **기존 층 재도전** — 해금 상한 안의 아무 층. **런 내부에서만**(회차 간 계승 없음) |
| 보상 체감 | **거리 체감 + 횟수 체감 병용** |
| 1군/2군 | **1군 = 최전선 정복 / 2군 = 파밍**(승급석·장비·경험치). 2군이 크면 1군과 교체 |
| 진행 방식 | **턴제** — 한 번에 한 군만 움직인다 |
| 정원 | **5 × 2군.** 1~20층은 3 유지, **21층부터 5 + 2군 개방**(로스터 8인부터) |
| 2군 정원 | **5. 모자라면 모자란 채로 출전** |
| 인원 이동 | **자유 편성 + 출전한 군은 다음 전투까지 교체 잠금** |
| 재튜닝 | **정원 5 유지 + 적 대폭 강화** |
| 회차(NG+) | 100층 클리어 후 컨텐츠. 보상은 파워가 아니라 **해금** |

### 2.1 "저층 재방문"이 아니라 "기존 층 재도전"이다

이름을 바꾼 것은 정확성 때문이다. 파밍 대상은 **해금 상한 안의 아무 층**이지
저층 고정이 아니다.

- 보상이 층 깊이에 묶여 있으므로 **스케일이 자동으로 맞고** `floorRewards`를 안 건드린다
- "1층 가서 성장"은 초반(5층쯤에서 3층 반복)에 실제로 그렇게 보이는 것이고,
  후반에는 고층 반복이 된다
- 실측상 **91~100층 파티(★6 Lv.95)와 1층 보상은 규모가 세 자릿수쯤 어긋난다.**
  진짜 저층 고정 + 보상 스케일링으로 가면 왜 90층 주인공이 1층 잡몹에서
  90층치 경험치를 얻는지 설명이 안 되고, `floorRewards`의 층 깊이 근거가 무너진다

지금 병목이 84·90·99층이라, 실제로 필요한 건 "1층 반복"이 아니라
**"90층 앞에서 89층을 몇 번 더 돌아 전력을 채우는 것"**이다.

### 2.2 보상 체감을 둘 다 쓰는 이유

| 축 | 무엇을 막나 |
|---|---|
| **거리 체감** (최대 도달층과의 차이) | 스케일을 맞춘다. `maxFloorReached`에서 파생되므로 저장 필드가 안 는다 |
| **횟수 체감** (`revisits`) | 같은 층 고착을 막는다. 층을 갈아타게 만드는 압력 |

거리 체감만 쓰면 **같은 층 무한 반복이 안 막힌다** — 89층을 100번 돌면 100번치
보상이 나오고, 차단은 오직 HP·포션 소모에만 의존한다.
횟수 체감만 쓰면 스케일이 안 맞는다.

### 2.3 ⚠️ 1군/2군의 의미 — 내가 한 번 오해했고 사용자가 정정했다

**내가 처음 적은 것:** 두 군이 **같은 등반선** 위에 있다. 90층 앞에서 1군이 다치면
2군을 내보내 90층에 도전한다. 사실상 10인 로테이션.

**사용자 의도:**
> "1군은 메인 파티로 층을 정복해 가는 파티, 2군은 서브파티로 성장하면서 기회되면
> 1군 덱과 바꿀 수 있어. 승급석이나 아이템 파밍용으로 2군 파티가 주로 활용"

**후자가 옳고, 이 차이가 설계 전체를 가른다.**

- 두 군이 같은 층을 번갈아 치는 게 아니므로 **최전선 승률은 여전히 1개 파티 기준**이다.
  정원 5의 효과만 층별 승률에 들어오고, **2군은 승률이 아니라 성장 속도에 들어간다.**
  두 손잡이가 서로 다른 축에 붙어서 "어느 쪽이 효과였는지 못 가른다"는 문제가 안 생긴다
- **재도전 파밍과 맞물린다.** 재도전이 그냥 "같은 층을 또 돈다"가 아니라
  **2군에게 줄 일거리**가 된다. 두 시스템이 서로를 필요로 하는 구조라
  각각 도입하는 것보다 설계가 단단하다

> 내 최초 판단("정원 5와 2군 교대는 같은 문제를 두 번 푸는 것")은 **오해 위에
> 세워진 것이라 무효다.** HP는 애초에 병목이 아니었다는 지적 자체는 맞지만,
> 역할 분리 구조에서는 2군이 HP를 푸는 장치가 아니다.

### 2.4 2군 정원 5 — 따라오는 결과를 알고 고른 것

개방 조건이 로스터 8명이므로 **개방 직후엔 1군 5 + 2군 3**이다.
3인 파티는 실측상 깊은 층을 못 돈다(61~80 구간 완주 17%).

즉 **2군은 열리자마자 강한 게 아니라, 로스터가 두꺼워지면서 같이 자라는 구조**다.
초반 2군은 얕은 층에서 승급석·장비를 캐고, 인원이 5로 차면 더 깊이 내려간다.
규칙이 정원 상수 하나로 끝나는 것도 이점이다.

### 2.5 교체 잠금 — 몰빵 차단이 아니라 리듬 장치

내가 단점으로 "한 턴 기다리면 우회된다"고 적었는데, 그건 잠금을 **몰빵 차단
장치**로 볼 때의 이야기다. **리듬을 만드는 장치**로 보면 유효하고, 무엇보다
잠금이 있으면 "이 전투에 누굴 보낼지"가 **되돌릴 수 없는 결정**이 되어
퍼머데스와 결이 맞는다.

## 3. 설계 1/4 — 데이터 모델과 저장 (승인됨)

```
party: HeroInstId[]        →  squads: HeroInstId[][]    // [1군, 2군]
floorIndex: number         →  floorIndex + maxFloorReached
(신규) revisits: Record<number, number>   // floorId → 재도전 횟수
(신규) lockedSquad: number | null         // 직전 전투에 나간 군
```

### 3.1 `floorIndex`와 `maxFloorReached`를 가른다

지금 `floorIndex`는 **"현재 위치"와 "최대 진행도"를 겸하고** 클리어 시 +1만 하는
단방향이라, "1층으로 돌아간다"를 표현할 자리가 없다 (`runStore.ts`).

- `floorIndex` = **이번에 도전할 층.** 해금 상한 안에서 자유롭게 앞뒤로 움직인다
- `maxFloorReached` = **해금 상한.** 최전선 진행은 이 값이 오를 때만 일어난다

> ⚠️ **`towerCleared` 판정을 `maxFloorReached` 기준으로 바꿔야 한다.**
> 지금은 `isFinalFloor(floorIndex)`로 판정하는데, 재도전으로 아래층에 있을 수 있으니
> 그대로 두면 **100층을 깬 뒤 1층에 내려가면 클리어 플래그 판정이 깨진다.**

### 3.2 `squads`는 배열의 배열

`[[a,b,c,d,e],[f,g,h]]` 꼴이고 2군 미개방이면 `[[...],[]]`.

**"한 영웅이 두 군에 못 든다"는 스토어에서 강제하고 세이브 복원 시에도 교정한다** —
`save.ts`가 이미 장비 양방향 관계를 교정하는 것과 같은 자리다.

### 3.3 세이브 v1 → v2

`save.ts`에 자리가 이미 준비돼 있다 (`SAVE_VERSION = 1`, `migrate(run, _version)`,
주석 "나중에 포맷을 바꾸면 여기에 분기를 넣고 SAVE_VERSION을 올릴 것" — `save.ts:274`).

| v1 | v2 |
|---|---|
| `party: [a,b,c]` | `squads: [[a,b,c],[]]` |
| — | `maxFloorReached` = `floorIndex` (그 층까지 갔다는 뜻이니 정확하다) |
| — | `revisits: {}` |
| — | `lockedSquad: null` |

**손실 없이 올라간다.**

`lockedSquad`는 **저장 대상**이다 — 새로고침으로 잠금이 풀리면 규칙이 없는 것과 같다.
`finish()`에서 세팅하고 다음 전투 `start()`에서 해제한다. 퍼머데스·자동저장이
이미 `finish()`에 몰려 있어 **단일 지점 원칙이 유지된다.**

### 3.4 정원 상수가 잘못된 자리에 있다 (문제) — 해결은 §4.1

**지금 코드에 실재하는 구조 문제 2건이다** (2026-08-22 실측 확인):



원본은 `src/screens/BaseScreen.tsx:9`의 `export const PARTY_LIMIT = 3`이다.

## 4. 설계 2/4 — 편성 UI와 정원 규칙 (승인됨)

### 4.1 정원 규칙을 함수로 내린다

`game/data/party.ts` 신설. **상수가 아니라 함수여야 한다** — 층에 따라 값이 갈린다.

```ts
export const SQUAD_COUNT = 2;
export const SQUAD_OPEN_ROSTER = 8;   // 2군 개방 조건

/** 층별 정원. 1~20층 3, 21층~ 5 */
export function partyLimitAt(floorId: number): number
/** 2군이 열렸는가 — 로스터 8인 이상 AND 21층 이상 도달 */
export function squadsOpen(rosterSize: number, maxFloorReached: number): boolean
```

`BaseScreen.tsx:9`의 `PARTY_LIMIT`과 `climb-check.mts:97`의 복제값을 **둘 다 제거**하고
여기서 읽는다. `runStore.ts:56-57`의 역방향 의존도 같이 끊긴다.

> `game/data/`에 있어야 하는 이유는 CLAUDE.md의 "밸런스 수치를 하드코딩하지 않는다
> → `src/game/data/`"다. 정원은 이제 밸런스 수치다 — 실측상 **가장 센 손잡이**다.

### 4.2 화면은 `RosterScreen` 하나를 확장한다

**새 화면을 만들지 않는다.** 편성은 이미 여기가 담당하고(`onToggleParty`), 대기실은
STEP 20에서 "로스터가 20명이 돼도 높이가 안 변한다"를 얻으려고 목록을 떼어낸 곳이라
되돌리면 안 된다. 바뀌는 것은 **선택 대상이 두 개**가 된다는 것 하나다.

```
┌──────────────────────────────┐
│ 영웅            생존 8 / 9   │
├──────────────────────────────┤
│  [ 1군 3/5 ]   [ 2군 2/5 ]   │  ← 편성 대상 전환 (44px)
│      최전선         파밍      │
├──────────────────────────────┤
│  ⓵ 카드   ⓵ 카드              │  ← 소속 배지가 카드에 뜬다
│  ⓶ 카드      카드             │
└──────────────────────────────┘
```

- **탭이 아니라 "지금 편성 중인 군" 전환이다.** 목록은 항상 로스터 전원이고,
  카드를 누르면 **선택된 군**에 넣고 뺀다
- **소속은 카드 배지로 보인다**(`⓵`/`⓶`). 지금 `selected`(테두리)만으로는
  "어느 군인지"를 표현하지 못한다
- 다른 군에 이미 든 영웅을 누르면 **거기서 빼고 여기로 옮긴다.** 막지 않는다 —
  "한 영웅이 두 군에 못 든다"는 스토어가 강제하되, UI는 금지가 아니라 이동으로
  처리하는 쪽이 조작 수가 적다

### 4.3 교체 잠금을 화면에 세운다

`lockedSquad`가 걸린 군은 카드가 안 눌리고, 전환 버튼에 자물쇠와 **사유**가 뜬다.

```
[ 1군 3/5 🔒 ]  → "직전 전투에 나갔습니다. 다음 전투까지 편성할 수 없습니다."
```

> **사유를 반드시 적는다.** B안 선택 시 단점으로 "왜 지금 못 바꾸나를 UI가 설명해야
> 한다"고 적었다. 설명 없이 안 눌리면 **고장으로 읽힌다**(§5-6).

### 4.4 2군 미개방 상태 — 숨기지 않고 조건을 적는다

```
[ 2군  🔒 로스터 8인부터 ]
```

숨기면 "그런 기능이 없다"로 읽힌다. STEP 6에서 시설 4개가 전부 잠긴 채 열려
**"아직 열리지 않은 컨텐츠"로 오독됐던** 것과 같은 함정이다. 조건을 보이면 목표가 된다.

## 5. 설계 3/4 — 기존 층 재도전과 보상 체감 (승인됨)

### 5.1 층 선택은 `TowerMap`에 붙인다

**새 화면을 만들지 않는다.**

- 미니맵이 이미 100층 전체를 구간 접기로 보여준다(STEP 17). 해금된 층은 이름이,
  잠긴 층은 `???`가 뜬다 — "갈 수 있는 곳"을 이미 구분해 그린다
- 탭하면 그 층이 `floorIndex`가 된다. 잠긴 층(`> maxFloorReached`)은 안 눌린다
- 대기실의 `탑 입장`은 현재 `floorIndex`로 들어간다. 기본값이 최전선이므로
  **재도전을 안 쓰는 플레이어의 동선은 지금과 완전히 같다**

> 재도전 전용 화면을 만들면 최전선 진행과 파밍이 서로 다른 입구를 갖는데,
> 둘 다 "층에 들어간다"는 같은 행위다. 입구가 갈리면 같은 것을 두 곳에서 관리하게 된다.

### 5.2 보상 체감 공식

`floorRewards()`를 **건드리지 않고 바깥에서 곱한다.**

```ts
// game/data/revisit.ts — 튜닝 상수 단일 출처
revisitMultiplier(floorId, maxFloorReached, revisitCount) → 0.15 ~ 1.0
```

**거리 계수** — 최전선에서 멀수록 깎는다.

```
distance = maxFloorReached - floorId
dist     = clamp(1 - distance * 0.04, 0.15, 1)
```

10층 아래면 0.6배, 21층 아래면 0.16배, 그 밑은 하한 0.15. 최전선 근처(89층에서
90층 준비)는 거의 온전하고 1층 파밍은 무의미해진다 — **§2.1의 "1층 보상으로
Lv.95를 올릴 수 없다"를 수식으로 표현한 것**이다.

**횟수 계수** — 같은 층 고착을 막는다.

```
rep = max(0.3, 0.7^revisitCount)   // 1.0 → 0.7 → 0.49 → 0.34 → 0.3(하한)
```

**하한을 0으로 두지 않는다.** 보상이 0이면 그 층이 "가면 안 되는 곳"이 되어
미니맵의 죽은 칸이 된다. 0.3이면 "돌 수는 있지만 다른 층이 낫다"가 된다.

> ⚠️ **최전선 진행에는 안 걸린다.** `floorId === maxFloorReached`이고 첫 도전이면
> 두 계수 모두 **정확히 1.0**이다. 즉 **지금까지의 밸런스 기준선이 그대로 보존된다.**

### 5.3 무엇을 깎고 무엇을 안 깎나

| 보상 | 체감 | 이유 |
|---|---|---|
| exp · gold | **적용** | 성장 속도가 파밍의 대가여야 한다 |
| 승급석 | **적용** | 2군의 주 목적이라 안 깎으면 무한 파밍이 최적이 된다 |
| 장비 드롭 | **적용**(확률에) | 같은 이유 |
| 과제 보상 | **안 깎음** | `claimedQuests`가 이미 재수령을 막는다. 층당 1회뿐이라 파밍 대상이 아니다 |

### 5.4 `revisits`는 클리어했을 때만 올린다

`finish()`의 `cleared` 분기 안 — 퍼머데스·경험치 지급과 같은 단일 지점이다.

> ⚠️ **져도 올리면 "실패로 보상을 깎는" 이중 처벌**이 된다. 진 전투는 보상 자체가
> 없으므로(`reward`가 `cleared`일 때만 붙는다) 카운트만 오르면 순손실이다.

### 5.5 최전선 판정이 바뀐다

```ts
// 지금 (runStore.ts:608-617)
floorIndex: cleared ? Math.min(FLOORS.length - 1, s.floorIndex + 1) : s.floorIndex
towerCleared: s.towerCleared || (cleared && isFinalFloor(s.floorIndex))
```

```ts
// 바뀐 뒤 — 최전선을 밀었을 때만 maxFloorReached가 오른다
maxFloorReached: cleared && s.floorIndex === s.maxFloorReached
  ? Math.min(FLOORS.length - 1, s.maxFloorReached + 1)
  : s.maxFloorReached
towerCleared: s.towerCleared || (cleared && isFinalFloor(s.maxFloorReached))
```

> ⚠️ **`towerCleared`를 `floorIndex`로 판정하면 안 된다.** 100층을 깬 뒤 재도전으로
> 1층에 내려가 있으면 판정이 깨진다. `ResultScreen`이 `finish()`보다 먼저 뜨므로
> **거기서도 같은 기준을 써야 한다**(§5-17).

## 6. 설계 4/4 — 재튜닝 순서와 테스트 전략 (승인됨)

### 6.1 왜 튜너로는 못 고치나 — 순서가 여기서 결정된다

정원 5는 전 구간 100%다. 그런데 **`floor-tune.mts`로는 이걸 못 고친다.**

> 튜너는 **변형 번호를 고르는 도구**지 적을 강하게 만드는 도구가 아니다.
> 지금 변형 24개는 전부 3인 기준 후보라 **그 안에 5인용 난이도가 아예 없다.**
> 24개를 전부 돌려도 최선이 100%다.

그래서 **생성기 먼저, 튜너 나중**이다. 반대로 하면 "합격 변형 없음"만 100번 찍는다.

### 6.2 재튜닝 4단계 — 각 단계가 다음의 입력이다

**1단계. 적 기수 확장** (`floorgen.ts`) — 3~4기 → **4~6기.**

수치 배수가 아니라 **기수**로 올린다. §STEP 15가 확인했듯 지수는 0.008 폭에서
결과가 뒤집히는 칼날이고, 기수는 선형에 가깝다.

> ⚠️ **§5-19를 반드시 지킬 것.** 같은 디버프를 주는 적을 겹쳐 쌓으면 급격하게
> 무너진다(방깎 2기 → 8%, 광역 2기로 97%가 25%). 기수를 늘리면 **중복 확률이
> 구조적으로 올라간다** — 역할 중복 상한을 생성기에 명시적으로 걸어야 한다.

**2단계. 튜너 재생성** (`floorVariants.ts`) — 기준 파티를 5인으로 바꾸고 `--write`.

§5-52대로 **두 편성 중 나쁜 쪽**으로 판정하는 로직은 유지하되, 5인 편성의
"최악"을 다시 정의한다(탱커 빠짐 / 힐러 빠짐).

> ⚠️ §5-54는 "표를 비우고 시작하지 말라"고 하지만 **이번은 입력이 통째로 바뀌므로
> 명시적으로 비우는 게 맞다.** 그 함정이 말한 "전체 재계산이 필요하면 명시적 절차로"에
> 해당한다 — 자동으로 비워지면 사고고, 알고 비우면 절차다.

> ⚠️ §5-50: 한 번에 수렴하지 않는다. **"변형으로 해결 0"이 나올 때까지** 돌린다.

**3단계. `MAX_DEATH` 재설정 + 구간 완주율 확인** — 목표는 **25~40%**(소모전).

> ⚠️ **`MAX_DEATH`를 절대값이 아니라 정원 대비 비율로 잡을 것.**
> 지금 값은 3인 기준 절대값이라 5인에 그대로 쓰면 **사망 허용치가 상대적으로
> 헐거워진다.** 승률은 합격인데 매 층 2명씩 죽는 구간이 생기고, 그 대가는
> §5-22대로 다음 층에서 청구된다.

**4단계. `SEED_OFFSET` 재탐색** — **맨 마지막이다.**

> ### ⚠️ 이 단계를 앞에 두려다 고쳤다 — 이유를 남긴다
> 최초 순서는 이걸 1단계와 2단계 사이에 뒀는데 틀렸다. `SEED_OFFSET`은
> **초기 로스터의 잠재 계수를 정하는 값이라 저층(1~6층) 승률을 움직이고,
> 저층은 정원 3을 유지하는 불변 구간**이다. 즉 21~100층 재튜닝과 **독립**이고
> 튜너의 입력도 아니다. 중간에 끼우면 튜너 결과가 나빠졌을 때 적 기수 탓인지
> 시드 탓인지 못 가른다(§5-51).
>
> 마지막에 두는 또 다른 이유: **초기 로스터 6인 구성이 구현 2단계에서 확정된다.**
> 그 6인이 누구인지 정해지기 전에 시드를 탐색하면 헛일이다.

> ⚠️ §5-10: 계수 합 0만으로는 부족하다(합 0인 후보가 43%를 내기도 했다).
> **반드시 승률까지 확인**해야 하고 sim으로는 안 잡힌다(§5-9) — 별도 스크립트가 필요하다.

### 6.3 회귀 감지선 — 무엇이 안 변해야 하는가

재튜닝은 표를 통째로 갈아엎는 작업이라 **"안 변해야 하는 것"을 먼저 못 박는다.**

| 불변 | 근거 |
|---|---|
| **1~20층 sim 표** | 정원 3 유지 구간. 6층 70%/1.35, 12층 43%, 20층 55%가 **한 글자도 안 변해야 한다** |
| **최전선 첫 도전 보상** | 재도전 계수가 1.0이므로 변경 전과 동일해야 한다 |
| **세이브 v1 왕복** | v1 세이브가 v2로 손실 없이 올라오는가 |
| 기존 테스트 595개 | 신규분 제외하고 안 깨지는가 |

> ### ⚠️ 이건 "안전벨트"가 아니라 회귀 감지선이다
> 1~20층 표가 움직이면 "안전하다"가 아니라 **"안 건드리기로 한 곳이 움직였다 =
> 어딘가 잘못됐다"**는 신호다. STEP 24(`sample.ts` 분할)에서 이 감지선이 유일한
> 안전장치였다 — "옮기기만 했으니 같을 것"은 근거가 아니었고, sim 70줄을 파일로 떠서
> 비교한 것이 증명이었다.
>
> **절차:** 재튜닝 각 단계마다 `npm run sim`의 1~20층 부분을 파일로 떠서 diff한다.
> 한 글자라도 다르면 그 단계를 되돌린다.

### 6.4 테스트 전략 — 세 층위

**순수 함수** (Vitest) — `partyLimitAt` · `squadsOpen` · `revisitMultiplier` ·
v1→v2 마이그레이션. 경계값 중심(20/21층, 로스터 7/8, 최전선 첫 도전 = 정확히 1.0).

**스토어 왕복** — 저장 → 복원에서 `squads` 양방향 관계, `lockedSquad` 유지,
`revisits` 보존.

> §5-32: 태스크별 리뷰는 교차 결함을 구조적으로 못 본다. STEP 18에서 6개 태스크가
> 전부 통과했는데 최종 리뷰가 Critical 3건을 찾았고 **셋 다 저장→복원 경계**였다.
> **왕복 테스트를 최소 하나는 둔다.**

**측정 도구** (tsconfig 밖 — 정적 검사가 무력하다) — `climb-check.mts`가 `squads`를
알아야 한다. 지금은 "HP 높은 순 3인"인데 2군 파밍이 들어오면 모델이 실제 플레이와 갈린다.

> ⚠️ **§5-23:** 측정 도구가 실제 플레이와 다르면 **없는 문제를 만들어낸다.**
> 정확히 이걸로 "중층 완주 0%"라는 헛것을 한 번 봤다.
> ⚠️ **§5-28:** 고쳤으면 **반드시 한 번 실행할 것.** typecheck도 테스트도 이 파일을 안 본다.

### 6.5 ⚠️ 죽은 테스트를 경계한다

이 개편은 **조건 분기가 많다**(2군 개방 여부, 잠금 여부, 재도전 여부).
§5-31이 경고한 바로 그 조건이다.

> 이 프로젝트에서 **통과하지만 아무것도 검증 안 하는 테스트가 세 번** 나왔다.
> 전부 확률·조건 분기였다.
> **검증하려는 가드를 일부러 제거해 테스트가 실패하는지 확인한 뒤 되돌린다.**
> 실패하지 않으면 그 테스트는 없는 것과 같다.

최소 3곳에 적용한다: **2군 미개방 가드 · 교체 잠금 · 재도전 계수.**

## 9. 이 설계가 건드리는 잠금 규칙

`gdd-v3.md:243`이 회차 계승을 **기록뿐**으로 잠가놨다 —
영웅·재화·시설을 물려주면 `sim` 기준선이 회차마다 갈리기 때문이다.

**이 설계는 그 규칙을 안 건드린다.** 재도전 파밍은 **런 내부에서만** 일어나고,
회차 보상은 **파워가 아니라 해금**(새 영웅 종류/시설/임무/난이도 단계)이다.
`SEED_OFFSET`으로 6층 67%를 맞춘 작업이 회차마다 다른 의미를 갖는 일이 없다.

> 영웅 12종은 10슬롯(1군 5 + 2군 5) 대비 얇다 —
> **회차 해금 보상으로 종류 추가**를 검토하기로 했다. 확정은 아니다.
