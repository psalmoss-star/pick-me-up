# 엔딩 이후 — 회차 플레이 + 무덤 (설계)

> 2026-08-11 · 대상: `runStore` / `save` / `identity` / `BaseMap` / 새 화면 하나

---

## 1. 무엇이 문제인가

100층을 깨면 **게임이 정지한다.** `towerCleared`가 서면 대기실의 입장 버튼이 잠기고,
그 뒤에 할 일이 없다. 55% 승률의 최종 보스와 엔딩 연출(STEP 11)을 만들어놓고
그 다음이 비어 있는 상태다.

동시에 **퍼머데스의 기록이 휘발된다.** 지금 사망자는 `roster`에 `isDead=true`로 남고
`deathCount`로 세어지지만, 그건 "이번 런"의 것이다. 회차를 시작하면 사라진다.
20층을 오르며 잃은 영웅들이 숫자 하나로 요약되고 끝난다.

---

## 2. 무엇을 만드는가

**회차 플레이(New Game+)와 무덤(영구 기록).**

| 결정 | 값 | 왜 |
|---|---|---|
| 계승 범위 | **아무것도 계승하지 않는다** | 매 회차가 동등하게 팽팽하다. 1회차에 잡은 밸런스가 그대로 산다 |
| 영구 기록 | 사망자 명부 · 회차별 등반 기록 · 정상에 선 영웅 · 도감 | 퍼머데스가 축적되는 것이 보여야 한다 |
| 이름 봉인 | **회차를 넘어 유지** | 무덤 기록이 항상 유일한 한 명을 가리킨다 |
| 무덤 위치 | **거점 부감 맵(`BaseMap`)의 다섯 번째 장소** | 무덤은 메뉴가 아니라 **장소**다 |

### 왜 계승하지 않는가

메타 화폐나 시설 계승을 넣으면 2회차 저층이 쉬워지고, `sim`으로 잡은 층별 승률이
"몇 회차 기준인가"에 따라 갈린다. **밸런싱의 기준선이 사라진다.**
`SEED_OFFSET = 22537`로 6층 67%를 맞춘 작업(§STEP "발굴 진행도 연결")이
회차마다 다른 의미를 갖게 된다.

계승하는 것은 **기억뿐이다.** 그게 이 게임의 축(퍼머데스)과 같은 방향이다.

## 3. 구조 — 저장 파일을 둘로 나눈다

```
tower-of-picks:run     ← 현재 런. 회차를 시작하면 freshSlice()로 덮인다
tower-of-picks:legacy  ← 영구 기록. 어떤 경로로도 리셋되지 않는다 (새 키)
```

**왜 나누는가.** 한 파일에 두면 회차 시작이 "일부만 지우는" 작업이 되고,
`RunSlice`에 필드가 늘 때마다 "이건 지우나 남기나"를 판단해야 한다.
`save.ts`의 `serialize()`가 필드를 **명시적으로 고르는** 것과 같은 이유다(§STEP 3).
파일이 갈려 있으면 실수할 수 없다 — `clearRun()`은 `SAVE_KEY`만 지우므로
**퍼머데스가 무덤을 오염시킬 경로가 구조적으로 없다.**

### 데이터 모양

```ts
// src/stores/legacy.ts (새 파일)
export interface FallenRecord {
  name: string;          // 봉인된 이름. 표시와 중복 회피 양쪽에 쓴다
  title: string;
  star: Star;
  defId: HeroDefId;      // 초상화용 (아트는 재사용 허용)
  floorId: number;       // 죽은 층
  revealProgress: number;// "알아내던 중에 잃었다"
  runNo: number;
}

export interface RunRecord {
  runNo: number;
  reachedFloor: number;  // 도달한 최고 층
  cleared: boolean;
  deaths: number;
  summons: number;       // gacha.totalPulls
  endedAt: number;
}

export interface SummitRecord {
  runNo: number;
  heroes: { name: string; title: string; star: Star; defId: HeroDefId }[];
}

export interface Legacy {
  version: number;
  runNo: number;         // 현재 회차 (1부터)
  runs: RunRecord[];
  fallen: FallenRecord[];
  summit: SummitRecord[];
  codex: Record<HeroDefId, CodexEntry>;  // §3.1 참조
}
```

`legacy.ts`는 `save.ts`와 같은 규칙을 따른다:
**절대 던지지 않고**, 깨졌거나 없으면 빈 기록을 돌려준다.
무덤을 못 읽어서 게임이 안 뜨는 것이 기록 하나 잃는 것보다 나쁘다.

### 3.1 도감은 어느 쪽이 정본인가

`codex`는 지금 `RunSlice`에 있고(`runStore.ts:117`) `freshSlice()`가 비운다(`:277`).
`Legacy`에도 두면 **같은 데이터의 출처가 둘**이 되어 어느 쪽이 맞는지 모르게 된다.

→ **`legacy.codex`를 정본으로 삼는다.**

- `RunSlice.codex`는 **그대로 둔다**(화면·소환이 이미 읽고 있다).
- 회차를 시작할 때 `freshSlice()`의 빈 도감 대신 **`legacy.codex`를 넣어준다.**
- `summon()`이 도감을 갱신하면 `legacy.codex`에도 같이 반영하고 저장한다.

도감은 "이 세계에 어떤 영웅이 존재하는가"의 기록이지 이번 런의 소유물이 아니다.
회차마다 초기화하면 3회차에도 도감이 비어 있어 수집 요소가 성립하지 않는다.

> ⚠️ 이건 **계승 없음 원칙의 예외**다. 도감은 전력에 영향을 주지 않으므로
> 밸런스가 움직이지 않는다(§7). 재화·영웅·시설과는 성격이 다르다.

## 4. 기록이 쌓이는 지점

**`finish()` 한 곳.** 퍼머데스가 반영되는 유일한 지점이고(§STEP 1부터 유지된 원칙),
사망자 정보가 거기 다 있다.

```
finish()
  ├─ 기존: 사망 반영 · 발굴 진행도 · 경험치 · 보상 · 과제 · 저장
  └─ 추가: casualties → legacy.fallen 에 append + saveLegacy()
```

- 사망자는 **죽는 즉시** 명부에 오른다. 회차가 끝날 때 몰아서 쓰면
  중간에 그만둔 런의 사망자가 통째로 사라진다.
- `towerCleared`가 서는 순간 `summit`에 그 시점 파티 3인을 남긴다.
- `RunRecord`는 **회차를 시작하는 순간** 직전 런의 것을 확정해 append한다.

> ⚠️ **진행 중인 런은 `runs`에 없다.** 회차를 한 번도 시작하지 않으면
> `runs`는 비어 있고, 그게 맞다 — 아직 끝나지 않았기 때문이다.
> 무덤 화면의 "등반 기록"은 `runs`(끝난 런) + **현재 런을 별도 행으로** 보여준다
> (`floorIndex`/`deathCount`를 스토어에서 직접 읽는다). 두 출처를 합치지 말고
> **"진행 중"으로 표시**할 것 — 합치면 끝나지 않은 런이 기록으로 굳는다.

> ⚠️ 합성 제물은 명부에 올리지 않는다. `takenNames`가 제물의 이름을 푸는 것과
> 같은 이유 — **제물은 죽음이 아니라 흡수**다(`identity.ts:96`).

## 5. 이름 봉인 확장

지금 `takenNames(roster, defs)`는 **현재 로스터만** 본다. 회차를 시작하면 로스터가
비므로 1회차에 죽은 이름이 2회차에 다시 나온다 — 무덤에 "6층에서 전사"라고
적힌 이름의 영웅이 살아 걸어다니게 된다.

→ `takenNames`에 **봉인된 이름 집합을 추가로 받고**, `pull()`이 그걸 통과시킨다.

```ts
// identity.ts
export function takenNames(
  roster: readonly HeroInstance[],
  defs: Record<HeroDefId, HeroDef>,
  sealed?: ReadonlySet<string>,   // legacy.fallen의 이름
): Set<string>

// gacha.ts — pull()의 인자에 추가 (roster와 같은 자리, 같은 성격)
sealed?: ReadonlySet<string>;
```

`pull()`은 이미 이름 유일성 검사용으로 `roster?`를 옵셔널로 받고 있다(`gacha.ts:158`).
**봉인 집합도 정확히 같은 성격이므로 같은 방식으로 받는다** — 새 패턴을 만들지 않는다.

옵셔널로 두는 이유: 기존 호출부(테스트·`sim`)를 안 깨뜨리고,
`src/game/`이 `stores/`를 import하면 안 되기 때문이다(순수 계층 규칙).
**집합을 만들어 넘기는 것은 호출부(`runStore.summon`)의 일이다.**

어휘는 2,904조합이고 회차당 수십 명이라 고갈 위험은 없다.
(`generateIdentity`에 이미 `NAME_RETRY_LIMIT` 초과 시 `N세` 폴백이 있다.)

## 6. 화면

### 6.1 진입점 — 거점 부감 맵의 다섯 번째 장소

`BaseMap`은 광장(160,140)을 네 시설이 둘러싼 배치다. 상단 중앙(약 160,52)이 비어 있다.
거기에 **무덤**을 둔다.

```
        [무덤]          ← 새로 추가 (160, 52)
  숙소          훈련소
        (광장)
  합성소        무기창고
```

- **시설이 아니다.** 레벨도 비용도 업그레이드도 없다. 그래서 `Building`을 재사용하지 않고
  별도 도형(비석 + 그림자)으로 그린다 — 같은 상자로 그리면 "지을 수 있는 것"으로 읽힌다.
- 사망자가 0명이면 **터만 보인다**(미건설 시설과 같은 표현). 첫 사망이 나면 비석이 선다.
- 비석 수는 사망자 수를 **대략** 반영한다(1~3개 + "외 n"). 27명을 다 그리면 그림이 무너진다.
- `onSelect`는 `FacilityKind`만 받으므로 **타입을 넓혀야 한다** →
  `BaseMapSpot = FacilityKind | 'grave'`. `ORDER`(4종 순회)와 `SPOT`은 시설 전용으로 두고
  무덤은 별도로 그린다 — `SPOT`에 넣으면 `facilities[k]` 조회가 무덤에서 깨진다.

> ⚠️ **세로 여유를 확인할 것.** `BaseMap`은 이미 "건물이 위로 자라 위 칸 이름표를 덮는"
> 문제를 겪었다(`BaseMap.tsx:32-34`, y=78/146 → 92/186으로 벌려 해결).
> 무덤을 y≈52에 두면 **숙소·훈련소(y=92)의 Lv.3 지붕(최대 66px 상승 → y≈26까지)** 과
> 겹칠 수 있다. 비석은 낮게(≈20px) 그리고, 겹치면 무덤을 위로 올리는 대신
> **viewBox 높이를 216에서 늘릴 것** — 버튼의 `top` 계산 분모도 같이 고쳐야 한다(`:178`).

버튼을 7개로 늘리지 않는 이유: 375px에서 이미 여러 줄로 wrap되고(§STEP 8),
무엇보다 무덤은 **장소**로 읽혀야 한다. 부감 맵이 이미 그 은유를 갖고 있다.

### 6.3 회차 시작

**무덤 화면에서만** 시작할 수 있다. 조건은 `towerCleared === true`.

```
[ 새로운 등반을 시작한다 ]
  ↓ 확인 창
  "이번 런의 영웅 5명 · 장비 12개 · 금 1,240이 전부 사라진다.
   무덤의 기록은 남는다."
  [ 되돌아간다 ]  [ 시작한다 ]
```

되돌릴 수 없는 소멸이므로 확인을 거친다 — 합성 제물과 같은 원칙(§STEP 5).
확정하면 `freshSlice()`로 런을 갈아끼우고 `runNo`를 올린 뒤 즉시 저장한다.

## 7. 밸런스에 미치는 영향

**없어야 한다.** `freshSlice()`를 그대로 쓰므로 2회차의 출발은 1회차와 동일하다.

검증:
- `npm run sim` 표가 **완전히 동일**할 것 (층·적·파티 어느 것도 안 건드린다)
- `npx tsx climb-check.mts` 동일
- 이름 봉인 확장이 **난수 소비 순서를 바꾸지 않을 것** — `generateIdentity`는
  `taken` 집합의 크기와 무관하게 같은 횟수의 난수를 소비한다(재추첨이 걸리기 전까지).
  ⚠️ 봉인 집합이 커지면 재추첨이 늘어 난수가 더 소비될 수 있다 →
  **소환 시드 스트림이 이름 추첨 뒤에 오는 것이 없는지** 확인할 것(§5-18).
  현재 순서는 `rollStar → pickArchetype → rollHeroSeed → generateIdentity`라
  이름이 마지막이므로 안전하다. **이 순서를 바꾸지 말 것.**

## 9. 만들지 않는 것 (YAGNI)

- **메타 화폐 / 영구 강화** — 계승하지 않기로 했으므로 필요 없다
- **회차 난이도 상승** — 층 생성기가 이미 결정적이라 회차마다 다르게 하면
  `sim` 기준선이 회차별로 갈린다
- **무덤에서 영웅 복원** — `revivalTokens`와 같은 이유로 **절대 만들지 않는다**
- **회차 무제한 통계·그래프** — 기록 세 종류로 시작하고, 필요해지면 그때
