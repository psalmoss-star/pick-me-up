# HANDOFF — 지금까지의 상태와 다음 할 일

## 0. 이 프로젝트는 모바일 세로 전용이다

나중에 온 사람이 가장 먼저 알아야 할 것.

- **타깃은 모바일 세로.** 375×667(iPhone SE) ~ 430×932.
- **데스크톱도 모바일 폭으로 본다.** `App.tsx`가 480px 중앙 컬럼으로 감싼다. 넓은 화면용 레이아웃은 없다.
- **반응형은 `src/ui/useViewport.ts` 훅으로 한다.** 인라인 style을 쓰므로 미디어 쿼리가 없다.
  분기점은 480px 하나뿐 — 3단으로 나누면 인라인에서 관리가 안 된다.
- **Tailwind는 설정만 있고 쓰지 않는다.** 전역 지침과 다르지만 이 프로젝트는 인라인 style이 기존 패턴이다.
- 터치 타깃은 44px 이상. `Button.tsx`의 `TOUCH_MIN` 상수를 쓸 것.

## 1. 끝난 것 (테스트 495개 통과)

### 개체 고유 이름 (2026-08-07) — 같은 카드가 두 장 나오지 않는다

**증상:** 소환을 반복하니 「물결의 세인」 카드가 3장 나왔다(Lv.20/Lv.1/Lv.1).
이름·초상화·속성·스킬이 전부 같았다.

**원인은 두 개였다.**

| # | 결함 | 위치 |
|---|---|---|
| A | 이름이 개체가 아니라 **종류**에 붙어 있었다 | `types.ts` — `name`이 `HeroDef`에만 존재 |
| B | **등급이 곧 캐릭터**였다 | `gacha.ts` `filter(h => h.baseStar === star)` + `sample.ts`에 별당 정확히 1명 |

B 때문에 ★3을 뽑으면 반드시 `h_tide`가 나왔다. **둘 다 고쳐야 사라진다** —
A만 고치면 이름은 갈려도 초상화·역할이 같고, B만 고치면 중복이 확률적으로 계속 난다.

```
src/game/data/names.ts   # 이름 66 × 수식어 44 = 2,904조합 + 이명 26
src/game/identity.ts     # generateIdentity / displayName / displayTitle / takenNames
src/game/identity.test.ts# 19개
```

- **이름은 파생이 아니라 저장한다** (`HeroInstance.name?`). 요구가 "매번 다르다"가 아니라
  **"보유 중인 카드끼리 겹치지 않는다"** 는 로스터 전역 제약이라, 개체 시드만으로는 못 지킨다.
  충돌 회피로 시드를 다시 굴리면 그 시드가 결정하는 **잠재치까지 바뀐다.**
  저장식은 어휘 배열을 나중에 고쳐도 기존 영웅 이름이 안 변한다는 이점도 있다.
- **`displayName(inst, defs)`이 유일한 관문**이다 (`potentialOf`와 같은 패턴).
  `def.name`을 직접 읽는 코드가 하나라도 남으면 옛 개체와 새 개체의 표시가 갈린다.
  전투 쪽은 `battle.ts`/`encounter.ts` **두 곳만** 고치면 된다 — BattleScreen·BattleUnit·
  beats.ts는 평탄화된 `.name`을 읽으므로 자동으로 덮인다.
- **아트는 defId 키 그대로 둔다.** 초상화 재사용은 허용된 요구사항이고, 이름이 갈리면
  같은 그림이라도 다른 인물로 읽힌다.
- **죽은 자의 이름은 영구 봉인.** `takenNames`가 로스터 전체(사망자 포함)를 훑는다.
  같은 이름의 새 영웅이 나오면 그 무덤 기록이 무의미해진다. 합성 제물은 로스터에서
  완전히 제거되므로 이름이 풀린다 — 의도된 차이다(제물은 죽음이 아니라 흡수).

| 항목 | 결정 | 이유 |
|---|---|---|
| 사망 요구 과제 | **하나도 두지 않음** | 상실을 보상으로 바꾸면 영웅을 일부러 버리는 게 최적이 된다 |
| 무사망 보상 | 크게 걸지 않음 | 안전 플레이에 큰 보상을 주면 퍼머데스가 "피할 실패"로 격하된다 |
| 유물 보상 | **최종 층에만** | 저층에서 새면 이후 등반이 무의미해진다 (테스트로 잠금) |

| 노출 위치 | 브리핑(진입 전) + 결과(달성 시) | 진입 전에 봐야 어떻게 싸울지 바뀐다. 결과에서만 알리면 선택이 사라진다 |
| 결과 화면 배치 | 손실과 **같은 패널** | 기쁨과 상실을 분리하지 않는다는 규칙을 과제에도 적용 |

⚠️ **결과 화면은 `finish()`보다 먼저 뜬다.** 그래서 스토어의 `questGrants`를 읽는 게 아니라

두 경로가 갈리면 "화면엔 A라 했는데 창고엔 B가 들어온" 상태가 되므로
**RNG 유도식을 `questRng()` 하나에 가뒀다** — 호출부가 직접 조합하지 말 것.
이 일치는 `stores/quest.test.ts`가 잠그고 있다.

### STEP 10 — 경험치 지급 버그 + 연속 등반 측정 교정 ✅ 완료 (2026-08-10)

§STEP 9에서 "중층 완주율 0%"로 잡혔던 것을 파고든 결과, **버그 하나와 측정 결함 하나**였다.
밸런스(층별 승률 표)는 결국 **한 줄도 바꾸지 않았다.**

#### 1. 참전 영웅이 경험치를 못 받고 있었다 (실제 버그)

`floorRewards().exp`는 결과 화면이 **"Exp +80"으로 이미 보여주고 있었는데** 어디에서도
지급되지 않았다. 즉 **싸운 영웅은 영원히 레벨이 오르지 않았다.**
(훈련소 유휴 exp는 전투에 *안 나간* 영웅만 받으므로 이걸 대신하지 못한다.)

§5-12(엔진이 돌려주는 `survivors[].currentHp`를 스토어가 안 읽던 것)와 **완전히 같은 종류**다.
타입도 테스트도 안 잡았고, 화면이 거짓말을 하고 있었다.
→ `runStore.finish()`에서 참전·생존자에게 지급. 테스트 2개로 잠갔다
(`승리하면 참전 영웅이 경험치를 받는다` / `패배하면 경험치를 주지 않는다`).

#### 2. 층 보상이 깊이를 안 봤다

`exp: turnsElapsed * 20` — 층을 아예 안 읽어서 **20층 보상이 1층과 똑같았다.**
깊은 층을 오를 이유가 보상에 없고, 파티가 자라지 않아 구간을 이어 오를 수 없었다.

→ `depthMultiplier(floorId, k)` 도입. **exp k=0.35 / gold k=0.12**.
근거(구간 완주 동안 약 2레벨 상승을 목표로 역산):

```
저층 1~6   총 1125 exp / 2레벨분 1740 = 0.6배
중층 7~12  총 3816 exp / 2레벨분 4560 = 0.8배
상층 13~20 총 9252 exp / 2레벨분 9400 = 1.0배
```

깊어질수록 자급률이 오른다 — 초반은 합성·소환에 기대고 후반은 등반 자체로 자란다.
**1배를 넘기면(k=0.5) 합성이 필요 없어져 제단이 죽는다.**
금은 더 완만하게(0.12) — 금이 급증하면 상점·강화가 등반보다 강해진다.

#### 3. 진짜 원인은 측정 모델이었다 (밸런스 아님)

exp를 고쳐도 중층은 0% 그대로였다. 층별로 추적해보니 **8층에서 266회 중 236회가 끊겼다** —
sim은 8층을 80%로 재는데도. 진입 HP는 96%였으니 소모전 문제도 아니었다.

원인: **`climb()`이 생존자를 전부 내보내고 있었다.** 한 명이라도 죽으면 다음 층을 2인으로 쳤다.

```
8층(탈출) 인원별 승률 — 만피 300회
  3인 (완전체)     78%
  2인 (힐러 없음)   0%     ← 사망 한 번이 곧 구간 실패였다
  2인 (탱커 없음)   4%
7층 통과 후 3인이 온전히 남는 경우: 300회 중 33회 (11%)
```

실제 게임은 정원이 3이고 초기 로스터가 5라 **대기 인원으로 빈자리를 채운다.**
그걸 모델에 넣자(HP 비율 높은 순으로 3인 선발):

```
              이전 → 이후
  저층 1~6     45% → 71%
  중층 7~12     0% → 20%
  상층 13~20    1% →  9%
```

> ⚠️ **`sim`의 승률만 보면 이 문제가 안 보인다.** 7층은 승률 90%지만 **사망 1.16**이다.
> 이기긴 하는데 매번 한 명씩 죽는 층이고, 그 대가는 다음 층에서 청구된다.
> **승률과 사망을 함께 볼 것** — 승률만 보면 "합격"인 층이 구간을 무너뜨린다.

> ⚠️ **측정 도구가 실제 플레이와 다르면 없는 문제를 만들어낸다.** 여기서는 하마터면
> 멀쩡한 층 밸런스를 "완주율 0%"라는 이유로 뜯어고칠 뻔했다. 수치가 극단적으로 나오면
> **밸런스를 의심하기 전에 모델이 게임과 같은지 먼저 확인할 것.**

### STEP 11 — 엔딩 연출 ✅ 완료 (2026-08-10)

최상층을 깨도 대기실이 "등반 종료"로 바뀌고 버튼이 잠기는 것이 전부였다.
55% 승률의 최종 보스를 만들어놓고 깨고 나면 아무 일도 안 일어나던 상태를 마무리했다.

```
src/screens/ResultScreen.tsx  # 엔딩 패널 + 버튼 문구
src/game/data/floors.ts       # isFinalFloor() — 판정식 단일 출처
src/screens/BaseScreen.tsx    # 잃은 영웅 수를 deathCount에서 읽도록 교정
src/game/floors.test.ts       # isFinalFloor 테스트 3개
```

**엔딩을 대기실이 아니라 결과 화면에 뒀다.** 대기실은 "다음"을 고르는 곳이라 이미 끝난 뒤다.
마지막 일격이 떨어진 화면에서 끝나야 등반의 끝으로 읽힌다.
MVP 카드보다 **위**에 둔 것도 같은 이유 — 마지막 층에서는 이번 전투의 MVP보다
등반이 끝났다는 사실이 먼저다.

문구는 승리만 말하지 않는다:

```
    등 반 종 료
    정상에 섰다
    20개 층을 올랐다.
    그 길에 2명을 두고 왔다.          ← 사망자가 있으면 핏빛
    이름은 봉인되었다 — 같은 이름의 영웅은 다시 오지 않는다.
```

무사망이면 "아무도 잃지 않았다 / 드문 일이다"로 바뀐다.
버튼도 "대기실로" → **"기록을 남긴다"**.

알아둘 것:

- **엔딩 판정은 `isFinalFloor()` 하나로 가뒀다.** 결과 화면은 `finish()`보다 먼저 뜨므로
  스토어의 `towerCleared`를 읽을 수 없어(§5-17) **같은 판정을 두 곳에서** 해야 한다.
  각자 `floorIndex >= FLOORS.length - 1`을 적으면 층을 늘릴 때 한쪽만 고쳐진다.
- **`towerCleared && win`이어야 한다.** 최상층에서 져도 엔딩이 뜨면 안 된다(실측 확인).
- **대기실의 "잃은 영웅" 수를 `deathCount`로 바꿨다.** 예전엔 로스터에서 셌는데
  (`roster.length - alive.length`) 합성 제물로 사라진 영웅은 로스터에 없어 빠진다.
  결과 화면 엔딩과 숫자가 갈리면 둘 중 하나가 거짓말이 된다.

**남은 것: 엔딩 이후.** 지금은 등반이 끝나면 게임이 정지한다(대기실만 열림).

### STEP 15 — 적 스탯 깊이 배수 ✅ 완료 (2026-08-10)

STEP 14에서 "생성 구간이 전부 승률 100%"였던 것을 해결했다. **탑 100층이 실제로 성립한다.**

```
src/game/battle.ts          # BattleInput.enemyStatMult + buildEnemy(mult)
src/game/encounter.ts       # 층에서 배수를 유도해 주입
src/game/data/floorgen.ts   # enemyStatMultFor — 곡선 단일 출처
```

- **`allyAtkMult`와 같은 패턴이다.** 엔진은 "몇 층인가"를 모르고 **이미 계산된 배수만** 받는다.
- **배수는 `encounter.ts`가 층에서 유도한다.** 호출부(화면·스토어·sim)가 각자 계산하면
  하나라도 빠뜨린 경로만 조용히 쉬운 전투가 된다(§5-14와 같은 이유).
- **hp/atk/def에만 곱한다.** spd를 곱하면 적이 항상 선공하고, crit은 확률이라 1.0을 넘는다.
- **1~20층은 배수 1.0** — 검증된 승률 표가 그대로 보존된다(확인함).

측정된 곡선 (표본, 구간별 파티 200회)

```
21~35층  100%          ← 아직 여유
40~45층   99 / 95 / 87%
60~65층   95 / 25 / 77%
80~85층   79 / 48 / 100%
90~100층  53 / 85 / 100 / 63%   ← 100층 보스 63%·사망 1.60 (20층 55%와 비슷)
```

> ### ⚠️ 지수는 0.008 폭에서 결과가 완전히 뒤집힌다
> ```
> 1.031 → 100층 11.5배 : 40층부터 전멸
> 1.020 → 100층  4.8배 : 60층부터 전멸
> 1.015 → 100층  3.4배 : 현재 값 ✓
> 1.012 → 100층  2.6배 : 전 구간 100%
> ```
> §5-1의 "칼날"이 여기서도 그대로다. 만졌으면 **반드시 `npm run sim`**.

알아둘 것:

- **지수는 영웅 성장폭에서 역산한다.** ★5 Lv.60 → ★6 Lv.99가 등급 1.42배 × 레벨 1.65배
  ≈ **2.34배**다. 다만 영웅에는 장비·잠재치·개입·포션이 더 얹히므로
  성장 배수를 그대로 맞추면(1.012) 전부 100%가 된다. 조금 앞서게 잡아야 한다.
- **보스는 배수를 55%만 먹인다.** 보스 자체가 일반 적의 2~3배 HP라 같은 배수를 곱하면
  격차가 곱으로 벌어진다 — 90층 보스 층 32,959 vs 같은 깊이 일반 층 23,016,
  승률 4% vs 100%였다. **보스는 "수치가 큰 적"이 아니라 "다르게 싸워야 하는 적"이어야 한다.**
- ⚠️ **보스를 일반 적 풀에 넣지 말 것.** 천층/정상 pool에 `sovereign`·`tyrant`를 넣었더니
  81층에 **재의 군주(최종 보스)가 일반 적으로** 나왔고 100층엔 두 마리였다.
  적 HP 합이 47,781(파티 8,080)이 되어 승률 0%였다. 풀에서 빼자 81층이 1%→96%가 됐다.
- 61층 25%는 **구간 경계 표본**이다(파티 티어와 적 풀이 동시에 바뀐다). 65층은 77%로 회복한다.

### STEP 16 — 생성 층 이름 중복 해소 ✅ 완료 (2026-08-11)

**100층이 하필 19층과 같은 이름**이라, STEP 11에서 공들인 엔딩이 재탕 이름 위에서 떴다.

src/game/floors.test.ts    # 테스트 4개 추가 (25 → 29)

|---|---|---|
| 고유 이름 | 82 / 100 | **95 / 100** |
| 중복 이름 | 15종 | 5종 |
| 최소 간격 | 4 | **32** |
| 장소어 최대 사용 | 11회(옥좌) | 7회 |
| 장소어 최소 간격 | 1 (인접) | **7** |

알아둘 것:

- **어휘를 늘리는 것만으로는 안 풀린다.** 16×16=256조합이어도 무작위로 뽑으면
  생일 문제 때문에 중복이 수십 쌍 나온다. 조합 수는 **재추첨이 성공할 여지**를 만들 뿐이고,
  실제로 막는 것은 `pickName()`의 간격 규칙이다.
- **전체 이름만 비교하면 부족하다.** 처음엔 이름 간격만 걸었는데 21·22층이
  '창백한 옥좌' / '얼어붙은 옥좌'로 나왔고 옥좌가 80층 중 **11번**(기대 4.7) 쓰였다.
  수식어만 갈아끼운 이름이 연달아 나오면 조합기라는 게 드러난다 → **장소어 간격**(6)을 따로 건다.
- **이름 간격(20) > 장소어 간격(6)이다.** 장소어가 16종뿐이라 20을 요구하면 후보가 고갈돼
  오히려 이름 중복이 생긴다. 재추첨 24회 중 **앞 12회만** 장소어 조건을 지키고 이후 완화한다 —
  더 눈에 띄는 쪽(이름 중복)을 우선한다.
- **`nameCache`는 성능이 아니라 생존 조건이다.** 이름도 이전 층을 다시 계산하므로
  캐시가 없으면 STEP 14의 지수 폭발(테스트 5분 정지)이 그대로 재발한다.
- **`HANDCRAFTED_NAMES`를 문자열로 적었다.** `floors.ts`를 import하면 **순환 참조**가 된다
  (floors.ts가 floorgen.ts를 부른다). 손으로 짠 층은 20개뿐이고 더 늘지 않으므로
  목록이 낡을 위험보다 순환 참조가 나쁘다. 1~20층 이름을 바꾸면 여기도 고칠 것.
- **100층만 손으로 준다**(`SUMMIT_NAME = '잿불의 왕좌'`). 엔딩이 뜨는 층이라
  '무너진 중정' 같은 조합 이름이면 무게가 안 실린다. 나머지 보스 층은 조합으로 충분하다.

> ### ⚠️ §5-18(난수 밀림)이 여기서는 발생하지 않는다 — 이유를 알고 넘어갈 것
> 이름 추첨을 늘리면 "그 뒤 모든 것이 밀린다"고 생각하기 쉽지만, `floorgen.ts`의 `pick01`은
> **`(floorId, salt)`의 순수 함수**다. 순차 스트림이 아니라 순서 밀림이 구조적으로 없다.
> §5-18은 `gacha.ts`처럼 **RNG 스트림을 순서대로 소비하는** 코드에만 적용된다.
>
> 다만 **salt 충돌**은 확인해야 한다(실측: 106·145·158·245·506 5건).
> 전부 재추첨 분기라 동시에 쓰이는 경우가 드물고, 값이 같아도 서로 다른 배열
> (NAME_A 16 vs pool 6~7)을 인덱싱하므로 관측 가능한 영향이 없다.
> **검증은 실측으로 했다** — `npm run sim` 표가 1~20층·생성 표본까지 완전히 동일하다
> (6층 70%/1.35, 20층 55%/2.00, 100층 63%/1.60). 이름 외 필드는 한 줄도 안 변했다.

## 5. 함정 (이미 밟아본 것들)

1. **보스 수치는 칼날이다.** 골렘 HP 3200 → 승률 100%, 4300 → 1%. 3700에서 63%.
   반드시 `npm run sim`으로 확인할 것.
2. **탱커 어그로를 100%로 하면 파티가 불사가 된다.** 힐러가 탱커만 계속 회복한다.
   `TANK_AGGRO = 0.6`은 이 문제 때문에 확률로 만든 것이다. 확정으로 되돌리지 말 것.
3. **수비/호위 임무는 `enemyFocus` 없이는 형해화된다.** 적이 오브젝트를 노리지 않으면
   성문 HP를 1로 놔도 전투가 끝날 때까지 멀쩡하다.
4. **배너 확률 합만 검증하면 부족하다.** 풀에 해당 등급 영웅이 없으면 소환이 조용히 실패한다.
   `validatePool()`을 기동 시 호출할 것.
5. **능력치 체계를 바꾸면 적 수치를 전부 다시 잡아야 한다.** 한 번 겪었고 4회 반복 조정했다.
6. **화면이 허전하다고 정보를 빼면 더 나빠진다.** 모바일 대응할 때 아트를 줄이고 미니맵을 빼는
   방향으로 갔다가 "도스 시절 텍스트 게임 같다"는 지적을 받았다. 세로 공간이 부족한 게 아니라
   **플레이어가 할 일이 없는 게** 문제였다. 깎지 말고 개입·연출을 더할 것.
7. **`npm run sim`은 개입 없이 돈다.** 그래서 개입을 넣어도 표의 승률이 안 변한다.
   이건 정상이다 — 기준선은 개입 없는 상태여야 비교가 성립한다.
   개입 포함 승률을 재려면 `sim.ts`에 개입 목록을 주입하는 코드를 따로 써야 한다.
8. **개입의 재현성을 깨뜨리지 말 것.** 개입은 입력이고, 고를 때마다 같은 시드로 재시뮬레이션한다.
   "재생 중인 전투 상태를 직접 수정"하는 방식으로 바꾸면 시드 재현이 무너지고 밸런싱 수단을 잃는다.
9. **`npm run sim`이 커버하지 않는 밸런스 변경이 있다.** sim은 `sim.ts` 안에서 자체 파티를 만든다.
   그래서 `initialRoster()`(= 유저가 실제로 쓰는 파티)를 바꿔도 sim 표는 미동도 하지 않는다.
   실제로 초기 로스터에 시드를 부여해 6층 승률이 70%→52%로 떨어졌는데 sim 출력은 그대로였다.
   **테스트도 못 잡는다** — 스토어 테스트는 증가량 규칙만 보고 승률은 안 본다.
   초기 로스터·파티 구성을 만졌으면 별도 스크립트로 승률을 재라.
10. **개체 시드를 "아무 상수나" 고르지 말 것.** 초기 로스터 시드는 밸런스 상수다.
   후보에 따라 6층 승률이 18%~91%로 갈린다. 계수 합이 0인 것만으로 부족하고
   (합 0인 후보가 43%를 내기도 했다) 반드시 승률까지 확인해야 한다.
11. **승률이 0%/100%에 붙어 스탯 조정에 반응하지 않으면 밸런스가 아니라 구조 문제다.**
   10층이 정확히 0%(사망 3.00 = 전멸)였을 때 적 공격력을 205→158로 크게 낮췄는데도
   표가 전혀 안 움직였다. 원인은 **도발 적이 하나도 없어서** 적들이 힐러를 직접 때렸고,
   힐러가 먼저 죽으면 회복이 끊겨 결과가 이분법이 되는 것이었다. 도발형(`e_warden`)을
   한 기 섞자 0%→25%로 풀렸고, **그 다음에야** 공격력 조정이 선형으로 반영됐다(→61%).
   → 적 스킬 구성 / `enemyFocus` / 보호 대상 HP를 먼저 볼 것. 수치는 그 다음이다.
12. **엔진이 돌려주는 값을 스토어가 안 읽고 버릴 수 있다.** `battle.ts`는 처음부터
   `survivors[].currentHp`를 반환했지만 `finish()`가 그걸 무시해서 **모든 영웅이 매 층을
   만피로 시작**하고 있었다. 타입은 통과하고(옵셔널 아님, 그냥 안 쓴 것), 테스트도 안 잡았다.
   `HeroInstance.currentHp`의 주석은 "층 사이 자동회복 없음"이라 **문서와 동작이 어긋난 채**
   오래 남아 있었다. → 엔진 출력 필드가 실제로 소비되는지는 grep으로 확인할 것.
13. **`npm run sim`은 층간 상태를 구조적으로 못 잰다.** sim은 매 층을 `currentHp:0`(만피)으로
   **독립** 측정하고 층을 이어서 오르지 않는다. 그래서 층간 HP 유지처럼 "층을 넘나드는" 변경은
   sim 표에 **전혀** 나타나지 않는다 — 실제로 층간 HP를 켠 전후 표가 완전히 동일했다.
   §5-7(개입)·§5-9(초기 로스터)와 같은 종류의 사각지대이며, 이 영역은
   **`npx tsx climb-check.mts`(연속 등반)** 로만 측정된다.
   회복 0%면 저층 파티가 평균 1.76층에서 끊긴다는 것도 sim으로는 영영 알 수 없었다.
14. **밸런스 수치를 화면에서 다시 계산하지 말 것.** `FacilityScreen`의 합성소 전환율을
   처음에 `50 + level * 15`로 직접 적었다가 고쳤다. 표시와 실제가 갈라지면 유저가 보는
   숫자가 거짓이 된다. 화면은 `fuseEfficiency()` 같은 **실제 함수를 부른다.**
15. **`seedSource()`를 다시 부르면 고정 시드 환경에서 난수가 얼어붙는다.**
   장비 드롭을 `createRng(seedSource())`로 굴렸더니 **30전 내내 단 하나도 안 나왔다.**
   테스트 스토어가 `() => 42`를 쓰는데 시드 42의 첫 값이 0.6011이라, 드롭 확률 0.35를
   매번 똑같이 넘긴 것이다. 전투 시드(`get().seed`)로 바꿔도 같았다 — 그것도 42였다.
   확률이 0%로 고정되는데 **테스트는 통과하고 타입도 멀쩡하다.**
   → 전투마다 달라야 하는 난수는 **전투 시드 + 층 + 누적 전투 횟수**를 섞어 만든다
   (`runStore.finish()`의 `lootRng`). 개입은 이 셋 중 무엇도 바꾸지 않으므로
   재시뮬레이션해도 드롭은 고정된다 — "좋은 템 나올 때까지 개입 돌리기"가 막힌다.
   같은 함정이 강화에도 있어 `gearSeq`를 섞었다.
   **확률적 이벤트를 추가하면 실제로 분포를 찍어볼 것.** 0%도 100%도 테스트를 통과한다.
16. **아트 매핑은 타입이 안 잡아준다.** `artMap.ts`는 전부 `Record<string, ...>`에 fallback이
   있어서, 키가 틀려도 컴파일은 통과하고 **엉뚱한 그림이 조용히 나온다.** 실제로 전투 화면의
   황녀가 성문으로 그려지고 있었다(호출부마다 `id` / `sourceId`로 키가 달랐다).
   fallback 값과 정답이 같은 경우(`e_slime` → `'blob'` = fallback)는 반환값만으로 누락을
   판별할 수 없으니, **"서로 다른 대상이 같은 아트로 뭉치지 않는가"로 검사할 것**
   (`src/ui/artMap.test.ts`가 이 방식이다).
17. **결과 화면은 `finish()`보다 먼저 뜬다.** 과제 달성을 스토어 `questGrants`에서 읽게
   짰다가, 화면이 렌더될 시점엔 아직 비어 있어 **아무것도 안 보이는 상태**였다.
   `finish()`는 "결과 확인" 버튼을 눌러야 돌기 때문이다.
   → 화면은 같은 순수 함수로 **미리 판정**하고, 지급은 `finish()`가 한다.
   이때 두 경로의 RNG가 갈리면 보인 보상과 들어온 보상이 달라지므로
   **유도식을 `questRng()` 하나에 가둔다.** 호출부가 `seed ^ floorId ^ ...`를 직접
   조합하면 그 순간 갈라진다 — 실제로 처음엔 `createRng(seed)`로 대충 넣어 어긋나 있었다.
   전투 후 상태를 화면에 보여줄 일이 또 생기면 **"이 화면이 그 상태보다 먼저 뜨는가"를 먼저 볼 것.**
18. **난수를 소비하는 코드를 기존 추첨 사이에 끼워 넣으면 그 뒤 모든 것이 밀린다.**
   개체 이름 추첨을 `rollHeroSeed` **앞**에 두면 소환 영웅 전원의 잠재치가 이동한다 —
   이름 기능을 넣다가 밸런스가 바뀌는 것이고, **타입도 테스트도 안 잡아준다**
   (기존 테스트는 "시드가 존재한다"만 보지 "값이 얼마다"를 안 봤다).
   → 새 추첨은 **기존 추첨 뒤에** 붙이고, 변경 **전에 실측값을 떠서** 회귀 테스트로 박을 것.
   §5-15와 같은 뿌리다: 확률·난수는 조용히 틀리고 조용히 통과한다.
19. **같은 종류의 디버프를 주는 적을 겹쳐 쌓으면 급격하게 무너진다.** 16층을 방깎 적 2기로
   냈더니 8%(전멸), 호위 층인 19층을 광역 적 2기로 냈더니 97%→25%였다. 중첩 효과는
   선형이 아니다 — "조금 더 어렵게" 하려고 같은 적을 하나 더 넣으면 층이 통째로 뒤집힌다.
   한 기씩 다른 역할로 섞을 것.
20. **적 구성이 같으면 임무가 달라도 같은 전투가 된다.** 13·16층이 승률·사망·턴까지
   79%/1.01/10.6으로 완전히 동일했다. 층을 늘릴 때 기존 구성을 재사용하기 쉬운데,
   `floors.test.ts`의 "상층은 같은 적 구성을 두 번 쓰지 않는다"가 이걸 잡는다
   (실제로 이 테스트가 중복을 세 번 잡아냈다).
21. **`climb-check.mts`의 `MAX = 6`처럼 도구 쪽에도 낡은 상수가 박힌다.** 12층 확장 때
   층 데이터만 고치고 측정 도구를 안 고쳐서, 이후 모든 세션이 **6층까지만 재고 있었다.**
   sim이 못 보는 영역을 보라고 만든 도구가 정작 새 영역을 안 보고 있었던 것이다.
   §5-12(엔진 출력을 스토어가 안 읽음)와 같은 뿌리 — **도구도 데이터를 따라 커져야 한다.**
22. **승률만 보고 층을 합격시키지 말 것 — 사망을 함께 봐야 한다.** 7층은 승률 90%지만
   **사망 1.16**이다. 이기긴 하는데 매번 한 명씩 죽고, 그 대가는 다음 층에서 청구된다.
   3인 파티가 2인이 되면 8층 승률이 78% → **0~4%**로 무너진다. 층별 표는 전부 합격인데
   구간 완주율이 0%로 나오는 이유가 이것이다.
23. **측정 도구가 실제 플레이와 다르면 없는 문제를 만들어낸다.** `climb-check.mts`가
   생존자를 전부 내보내(정원 3을 무시) 사망 한 번이 곧 구간 실패가 되도록 재고 있었다.
   대기 인원 교체를 넣자 중층 완주율이 0% → 20%가 됐다 — **밸런스는 한 줄도 안 바꿨다.**
   하마터면 멀쩡한 층을 뜯어고칠 뻔했다. 수치가 극단적으로 나오면 밸런스를 의심하기 전에
   **모델이 게임과 같은지 먼저 확인할 것.**
24. **화면이 보여주는 수치가 실제로 지급되는지 확인할 것.** 결과 화면은 "Exp +80"을
   오래전부터 보여주고 있었지만 `runStore.finish()`가 지급하지 않아 **싸운 영웅은 영원히
   레벨이 안 올랐다.** §5-12(엔진의 currentHp를 안 읽던 것)와 같은 뿌리다 —
   계산해서 화면에 넘기는 것과 상태에 반영하는 것은 별개이고, 타입도 테스트도 안 잡아준다.
25. **생성기에 규칙을 넣을 때 "무엇이 눈에 띄는가"를 축마다 따로 물을 것.** 층 생성기는
   적 구성에만 중복 회피가 있었고 **이름에는 없었다** — 그래서 100층이 19층과 똑같이
   '잿빛 회랑'이 됐다(엔딩이 재탕 이름 위에서 떴다). 이름은 화면 상단에 글자로 박혀 있어
   구성보다 **훨씬 쉽게 기억된다.** 축마다 요구 간격이 달라야 한다(이름 20 > 구성 8 > 장소어 6).
   → 한 축에 규칙을 걸었다고 다른 축이 보호되는 게 아니다. **생성물을 실제로 나열해 볼 것** —
   82/100이라는 숫자는 코드를 읽어서가 아니라 찍어봐서 나왔다.
26. **어휘를 늘리는 것은 중복 대책이 아니다.** 12×12=144를 16×16=256으로 늘려도
   무작위 추첨이면 생일 문제로 중복이 수십 쌍 나온다(실제로 늘린 직후에도 10종이 남았다).
   조합 수는 **재추첨이 성공할 여지**를 만들 뿐이고, 실제로 막는 것은 간격 규칙이다.
   같은 함정이 §5-15(확률은 조용히 틀린다)와 뿌리가 같다 — **분포를 찍어보기 전에는 모른다.**
27. **`pick01(floorId, salt)` 같은 순수 해시에는 §5-18(난수 밀림)이 적용되지 않는다.**
   추첨을 늘려도 순차 스트림이 아니라 뒤가 밀리지 않는다. 대신 **salt 충돌**을 봐야 한다.
   §5-18을 기계적으로 적용해 "이름을 건드리면 밸런스가 바뀐다"고 겁먹지 말고,
   **그 코드가 스트림인지 순수 함수인지 먼저 구분할 것.** (판단 후에도 검증은 `npm run sim`으로.)
28. **스크립트를 폴더로 옮기면 상대 경로가 깨지는데 아무도 안 알려준다.** σ 도출 근거 5개를
   `scripts/`로 옮기면서 파일 안의 `from './src/game/...'`를 안 고쳐 **전부 실행 불가**였다
   (24곳). "근거를 남기려고 옮긴 파일이 정작 돌아가지 않는" 상태가 조용히 유지된다 —
   `npm test`도 `npm run typecheck`도 이걸 **못 잡는다**(스크립트는 tsconfig include 밖이고
   테스트가 부르지도 않는다). §5-21과 같은 뿌리다.
   → **파일을 옮겼으면 한 번 실행해 볼 것.** 정적 검사는 여기서 무력하다.
   (`gen-art.mts`는 `import.meta.url` 기준이라 안 깨졌다 — 경로를 자기 위치에서 유도하면 이 함정이 없다.)
29. **`column-reverse`와 `grid`를 섞으면 같은 화면에서 방향이 반대가 된다.** 미니맵은
   "아래에서 위로" 쌓는데, 잠긴 층 격자를 `known`보다 DOM 앞에 뒀더니 **안 오른 층이
   현재 층보다 밑에** 깔렸다(1층 top=600, 2층 640). 격자 내부도 채우기가 좌→우·위→아래라
   **낮은 층이 맨 윗줄**에 온다(2층 825 vs 20층 848). 10칸씩 끊어 행 단위로 뒤집어야 맞는다.
   → **테스트가 절대 못 잡는다.** 데이터는 완벽히 맞고 순서만 뒤집힌 것이라
   `npm test`·`typecheck` 전부 통과했다. **브라우저에서 좌표를 재야** 보인다
   (`getBoundingClientRect().top` 비교). 방향성 있는 레이아웃은 스크린샷만으로도 놓치기 쉽다 —
   실제로 스크린샷을 보고도 못 알아채고 좌표를 재서 찾았다.
30. **`import.meta.glob`은 Vite 전용이라 tsx 스크립트에서 터진다.**
   진단 스크립트가 `runStore`를 import했더니 `ui/art/heroImages.ts`까지 딸려와
   `(intermediate value).glob is not a function`으로 죽었다.
   → CLI 진단은 `src/game/`의 순수 계층만 건드릴 것. 스토어를 거치면 UI가 따라온다.
